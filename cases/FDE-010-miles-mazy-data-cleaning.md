## 一句话摘要

这篇的价值不在"做了一个什么项目"，而在"数据脏到没法用时，一步一步怎么洗干净"：一家美妆企业要做舆情分析、竞品调研和营销活动复盘，数据已经从小红书、抖音、视频号、微博采回来了，但文字、图片、音频、视频混在一起，同一个产品有多个叫法，原帖、评论、回复的关系还不能丢。作者给出的答案是一条八步清洗链路——先定规范、原始内容永保留、关系先理清、多模态归一、冲突看证据、重复与异常分流、结构化成可查询数据、验收后按版本入库。这是本库目前数据与集成环节讲得最完整的一张卡，也是 FDE-005 之后第二张值得当"数据环节教科书"对照读的国内方法文。

## 全流程 7 环节拆解（只引来源真实讲到的）

### ① 选场景
- **业务已经定下来了，选场景的决策过程没写**：舆情分析、竞品调研、营销活动复盘，以及从评论区提取用户对功效、肤感、成分、价格和使用场景的真实反馈。这四个用途是全文的前提，但客户为什么先做这四个、排了什么优先级：来源未披露。
- **可迁移的一点**：场景落在"已经发生的真实讨论"上，不是新造一个 AI 功能。数据清洗这个环节本身，就是因为业务要"从评论区里读出真实反馈"才成立的。

### ② 摸现场
- **现场的脏，是四种脏叠在一起**：多平台（小红书、抖音、视频号、微博）数据已采集回来；文字、图片、音频、视频四类模态混杂；同一产品有多个叫法；原帖、评论、回复之间的关系必须保持完整。摸现场的结论就是这四句，没有平台量级、采集周期、数据量数字。
- **一个容易被忽略的现场前提**：数据是"已采集回来"的，采集环节本身（爬取、合规授权、反爬）怎么做的：来源未披露。引用时不能把这篇当成采集方案。

### ③ 定方案
- **方案的第一步不是选工具，是先问用途**：同一批数据最后拿来干什么，用途不同清洗方式就不同。作者举的例子是：同一条种草素材被十个账号发布，做传播复盘要保留全部，做自然讨论统计则标为一组重复。用途先行，是全文最值得抄的一句话。
- **规范要先写清五件事**：必须保留的字段、帖 / 评论 / 用户的关联方式、哪些判断必须附原文、哪些数据可直接使用、哪些需人工确认。规范先行于清洗，是这篇与"直接上模型洗"的做法最根本的区别。

### ④ 数据与集成
- **原始内容永远保留**：原文、图片、音频、视频、链接、发布时间、平台原始 ID 全部保留；清洗后文本另存，不覆盖原文；OCR、ASR、模型标签只能作为新增结果。好处作者写得很实在：可回查、可换模型重跑、报告结论能找到证据。
- **关系梳理分平台内与平台间两层**：单平台至少保留 user_id、post_id、comment_id、parent_comment_id 四类 ID，主键可用"平台名 + 平台原始 ID"；跨平台不直接"认人"，昵称 / 头像相同只算线索，无可靠主键和授权时只汇总话题、对象和内容。概括成一句：平台内把关系梳理清楚，平台间把来源分开保存。
- **多模态分别处理，再统一格式**：最终统一为"谁在什么时间说了什么、提到什么对象、证据在原内容哪个位置"。文字保留原文后处理乱码 / 空白 / 链接 / 语言 / 重复段落，模型提取观点要返回对应原句；图片 OCR 提取价格 / 型号 / 日期 / 截图文字，视觉模型识别对象、场景、部件，两者都保留图片位置；音频先统一格式与采样率再做 ASR（带时间码），多人对话加说话人区分；视频拆音轨 + 关键帧，音轨 ASR、关键帧 OCR / 视觉识别，按时间合并，无需逐帧，先低频抽帧全文转写再对相关片段提高密度。
- **工具选型写明了取舍**：小批量直接调 API，量稳后高频任务搬本地。提及的工具与服务：FFmpeg（拆音轨 / 转码 / 抽帧）、PaddleOCR（本地 OCR）、Whisper（本地语音识别）、云端 OCR（百度智能云 / 腾讯云）、云端 ASR（腾讯云 / 火山引擎音视频字幕生成）。上线前要看控制台额度与并发限制，用真实样本测试方言、噪声、中英混合、竖屏字幕、截图小字。作者还建议做一个轻量工作台：文件 / 链接进入 → 自动选工具 → 查看原文与识别结果 → 人工修正 → 导出 JSON / CSV，并记录调用次数、耗时、费用、失败原因。
- **冲突处理是全文最硬的一段**：一条视频 ASR 识别成一个数、画面 OCR 识别成另一个数时，不能只信置信度高的一方。证据分级五档：A 级（官方字段 / 人工确认）、B 级（原图原音原视频可直接确认）、C 级（多模型一致且上下文对上）、D 级（单个模型识别判断）、E 级（关键词 / 正则 / 简单规则候选）。处理流程是：按时间码和图片位置找原始证据、核对单位 / 上下文 / 发布时间；能确认就修正，不能确认就进入待核队列、不参与精确数值统计；修正时保留原值、修正值、证据等级、原因、复核状态、模型版本，原值不覆盖。
- **重复、低质量、异常分开处理**：先筛相关内容（关键词词典找全 + 语义模型补简称、缩写、相近说法），再处理重复（完全复制 / 轻微改写 / 同图不同文 / 同视频再发布归入同一重复组，原始记录保留，统计时再定按帖 / 素材 / 账号去重），最后识别异常（发布时间、内容相似度、账号历史、发帖节奏、互动网络为信号）。系统输出四种状态：正常可用、重复关联、低质量（待修复或隔离）、高风险（人工复核）。风险分只用于排序，活动统一素材、媒体矩阵、合作账号也高度相似，不能见高分就删。

### ⑤ 开发交付
- **交付物是链路 + 工作台，不是单个模型**：八步链路本身、轻量人工复核工作台、JSON / CSV 导出，是文中明确写出的交付形态。工作台的记录字段（调用次数、耗时、费用、失败原因）是交付可审计性的关键。
- **结构化是开发交付的收口**：用户评价不能只打"负面 / 中性"标签，要整理成五类结构：表达者与评价对象、提到的产品 / 部件 / 功能 / 服务、对象间发生什么、用户观点 / 问题 / 意图、判断依据（哪句原文 / 图片位置 / 音频段）。高频规则稳定任务给规则和小模型，多语种 / 多对象 / 复杂指代 / 长文本给大模型，低置信进人工复核；大模型按固定 JSON 返回字段和证据，字段名 / 可选值 / 空值规则提前写清。
- **验收是交付的门，不是事后检查**：检查原始内容链接完整、评论可回溯原帖和上级评论、OCR / ASR / 视觉结果带位置、冲突有处理状态、标签绑定正确对象、规则模型字段有版本号；准备人工确认的测试样本（含正常和难例），每次换规则 / 模型都重跑；入库时原始数据、处理结果、质量状态、版本信息分开保存。

### ⑥ 上线采用
- **验收与版本入库写了，采用本身没写**：谁在用这套清洗后的数据、业务方是否采信报告结论、有没有因为数据质量问题返工、培训与交接怎么做：来源未披露。验收清单与版本记录是上线采用的前置条件，不是采用证据，引用时不能偷换。
- **下一篇预告不是已交付**：作者文末说下一篇将讲 Elasticsearch 查询与可信报告。这是作者的写作计划，不是本项目的交付内容，不得写成已发生的迭代。

### ⑦ 迭代扩单
- 扩到新品牌、新业务线、新平台的具体路径：来源未披露。全文只讲了"把业务规则、数据处理、模型能力和人工复核接成长期运行的流程"这一判断，没有写扩单事实。

## 对入行者的启示

- **数据环节的第一课是"用途先行"，不是"工具先行"**：同一批数据，传播复盘和自然讨论统计的去重口径完全相反。面试讲数据项目时，先讲用途怎么定规范，再讲用了什么模型，顺序本身就是专业度。
- **原始内容永保留，是 FDE 数据工作里最便宜的后悔药**：OCR、ASR、模型标签只能做新增结果，不能覆盖原文。换模型重跑、报告结论回查、客户质疑时拿证据，全靠这一条。自己的项目里先把这条写进规范，再谈准确率。
- **冲突不要只信置信度，要信证据等级**：ASR 与 OCR 打架时，按时间码和图片位置找原始证据，确认不了就进待核队列、不进精确统计。这一条直接对应 FDE-008 的 Eval 先行：评估与证据，都是"结论能不能追溯到原文"的问题。
- **风险分只排序，不删帖**：活动统一素材、媒体矩阵、合作账号天然高度相似，见高分就删会把正常营销内容当水军清掉。做异常识别时，先分流、再人工复核，删除永远是最后一个动作。
- **验收清单可以直接抄去当交付 checklist**：链接完整、评论可回溯、识别结果带位置、冲突有状态、标签绑定正确对象、字段有版本号——这六条过不了，数据就不能叫"可信数据"，只能叫"跑过模型的数据"。

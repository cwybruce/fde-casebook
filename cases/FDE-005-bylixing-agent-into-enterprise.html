一句话摘要

中文语境第一篇甲方视角的企业 Agent 落地长文：作者本人就是那个"一个人搭完全公司 Agent 底座"的人，结论极硬——模型决定上限，上下文和闭环决定实际发挥，而组织机制决定上下文和闭环能不能建起来；落地八成是组织和利益问题，不是技术问题。

全流程 7 环节拆解（只引来源真实讲到的）

① 选场景

  • 增量优先，不在存量里内卷：存量里用 AI 省人 = 动某个人的地盘，阻力最大；用增量分增量，阻力最小。作者类比孝文帝迁都：不在旧都和旧贵族硬碰，换新地盘重新分配。
  • 双赢先行：投放团队先跑通——优化师自己摸索让 Agent 操控浏览器点广告后台，粗糙但证明了真需求，公司再收编成稳定工具。
  • 样本按光谱选：模型公司只看方向不抄打法；和自己在"数字↔物理光谱"上位置相近的先行者，踩的坑才是你会踩的坑。OpenAI / Anthropic 领先半年到一年，但它们全在数字端。
  • 两个自检问题：① 公司里正在发生的事，Agent 看得见吗？② Agent 做了一个判断，它能知道结果好不好吗？

② 摸现场

  • 老板先下场，当联席 CEO：必须一把手亲做的两个理由——只有一把手天然站在公司整体利益上（部门与员工都只优化局部）；一把手亲手用过才知道能力边界，不会被忽悠。
  • 判断不一致三分法：Agent 判断和老板不一致时，原因只有三种——信息没给到（技术活）／模型能力不够（等升级或换顶级模型）／公司压根没记录（最有价值，暴露只活在某人脑子、微信群、口头里的组织漏洞）。
  • 补货闭环样例：补 500 件的理由记在表上 → 一个月后回填实际销量／断货／压货 → Agent 对理由与结果找偏差（如没算大促）→ 沉淀成规则，下次补货前先读。教训不会自动进模型，只能记在 Agent 下次一定会读到的地方。

③ 定方案

  • 二流解：老组织架构下小步调整，先提效，再从业务发展中找调整点。一流解（把 Agent 当正式成员、围绕它重构组织架构与分钱）只适合从零开始的新组织。
  • 载体判断：飞书多维表格是作者原话定性的"目前国内最好的、同时面向人和 Agent 的协作型数据库"——人随手改、手机拍照上传，Agent 有现成读写通道，权限与离职回收等琐事平台已做好；自研系统每加一个字段要走需求—排期—开发—测试，而业务策略一天一变，等不起。
  • 记多细的标准：看这条信息在业务闭环里是否真起作用。帐篷差评"漏水"：只记"库存 1000 件"闭环就断了；记到批次／供应商面料／质检，Agent 才能定位到某批次某供应商，决策完差评率再回验——闭环才转起来。
  • 分工边界：几百万行广告历史数据进正规数据库；需要人机共同维护的状态类信息才上飞书表。会议录音转文字存档是最低成本起步动作。

④ 数据与集成

  • 一张表串商品一生：内外部五六个系统定期汇总到飞书多维表格，商品全生命周期的状态、决策理由与结果回填都在同一处。
  • 外部两小时，内部两个月：外部平台数据调接口／模拟浏览，几小时接进来；内部满意度回访线推了两个多月，大部分时间耗在权限、申请、责任归属的协调上。技术的墙常比部门的墙好翻。
  • 信息税：每多记一条信息 = 给业务流程加一道"税"。供应链同事拜访供应商，以前口头对一下就行；现在要求全程录音、关键节点拍照、上传建档——对公司价值极大，对同事本人价值答不上来。税重了必然不填／乱填／应付填，表上信息反而失真。
  • 动手前两问：这条信息真能改变某个决策吗？一线多花的那几分钟值不值？不值别记；值，就先把那几分钟压到接近零（录音自动转写归档、拍照一键完成）。作者自承供应链这条至今无好解法，只能定制度 + 重点产品强推。

⑤ 开发交付

  • 搭戏台，不写剧本：架构师先搭统一数据源／权限／工具平台／反馈机制，再观察"野生做法"，传播开了就收编正规化。顺序铁律：先有人走出路，公司再修路，不要预判需求闷头开发半年。
  • 收编正例：投放优化师操控浏览器点广告后台（野生做法）→ 公司把广告操作能力正式开放成稳定工具 → 员工省心且多赚钱，公司盘子变大，双赢，自己长，不用推。
  • 模型分层 = 成本结构：执行层用最便宜最快的（作者一线全用 DeepSeek Flash 档）；决策层舍得用最顶级的，甚至多家顶级模型交叉讨论；折中模式：杂活便宜模型干，关键判断把整理好的信息交给顶级模型"只借它最贵的那几分钟"。不要用 Token 消耗量衡量落地效果，要看业务结果。

⑥ 上线采用

  • 分配先于考核：10 万能不能变 15 万——优化师月广告消耗 10 万，用 AI 后还是 10 万只是更轻松，算不算价值？作者分两层：分配和目标不变时，"更轻松"就是 AI 能给他的全部；想变 15 万本质是分配问题，不是 KPI 问题（指标成考核目标就失真，古德哈特定律）。公司真正想要的是"业务扩大 10 倍、人只增 2 倍"，得先想多出来的收益怎么分，再谈考核。作者坦白：新的分配方式自己也还没落地，此节是想法层推演。
  • 绝对禁区：谁贡献了工作流，谁就被裁——下一个人学到的就是"把经验藏好"，转型氛围直接废掉。
  • 悖论：谁 AI 用得越好，谁越不需要公司。最该留住的恰是最有能力离开的人（既懂业务又能自己搭工作流），要舍得分钱，让他觉得留下比单干划算。
  • 人员金字塔：顶层 Agent 架构师 1–2 人（既懂 Agent 又懂业务，作者公司就是他一个人；找不到时的次优解是老板自己去懂 Agent）；中层积极分子 3%–5%（真实业务里用出成绩、沉淀工作流给其他人抄；大多数人"因为看见所以相信"）；基层大多数不用懂 Agent，按沉淀好的流程点按钮／走审批，核心职责是低摩擦地留下下一轮 Agent 需要的信息。不要追求 100% AI 使用率，不要搞全员培训人人学提示词。
  • 上行下效：老板天天对着表决策，其他人自然被迫在表上协作；负责人汇报前必须带来表上没有的东西。

⑦ 迭代扩单

  • 定时巡检与跨源发现：Agent 定时巡检拦截问题（该上架的卡了 20 天、客诉率到警戒线没人管）；上下文够厚时，让最强模型跨几十个数据源找"销量为什么掉了"的意外关联。

对入行者的启示

  • 面试要补甲方视角：此前案例库多为乙方视角，这篇是甲方老板亲述"乙方进来会撞什么墙"——权限两个月、信息税、分配先于考核。面试讲 FDE 时能说出"落地八成是组织问题，我会先找双赢的增量场景"，是明显的认知差。
  • 摸现场先找双赢的增量场景：别在存量里动人地盘；先让一线"因为看见所以相信"，再谈扩面。
  • 利益清单是上线采用的硬输出物：谁出力、谁受益、多出来的收益怎么分——写不清楚，推广会在会议室里被耗死；考核指标一旦立起来就会失真，别拿使用率和 Token 量当验收。
  • 模型分层是成本观：执行层便宜模型、决策层顶级模型；不要用 Token 量衡量落地效果，要看业务结果。
  • 样本按光谱选：别照搬数字端大厂的打法，和自己在数字↔物理光谱上同位的先行者，踩的坑才是你会踩的坑。

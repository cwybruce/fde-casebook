## 一句话摘要

数据洗干净之后，客户要的不是"演示能跑"，而是每天能稳定跑、结果准、还能回溯证据的取数查询。这篇是 FDE-010 的直接续集：客户的新需求是查过去 30 天某款精华在小红书和抖音的口碑，作者用四次真实踩坑讲清了为什么"演示能跑"不等于"生产可信"——AI 直接写查询会把多产品同帖的情感算错人，固定模板稳住了格式却稳不住"声量"这种业务词的意思，让 AI 像分析师一样点页面会在第二、第三轮开始混进上一轮的筛选条件，直接调业务 API 又会因为缺了前端才知道的上下文而返回"看起来正常、实际无用"的数据。最终解法是把高频需求做成 Tool、让 AI 通过 MCP 发现并调用，AI 只确认有限条件，内部查询与业务规则留在 Tool 内；但作者明确提醒，接入 MCP 本身不会自动保证准确，业务规则仍需人工定义。

## 全流程 7 环节拆解（只引来源真实讲到的）

### ① 选场景
- **真实高频问题，值得做成每天稳定运行的方案**：查过去 30 天某款精华在小红书和抖音的口碑，大家主要在讨论保湿、抗老、肤感还是香味，负面评价集中在哪里。这不是一次性演示需求，是客户每天都要问的问题，选场景的判据就是"高频 + 每天都要准"。
- **核心矛盾先讲清**：演示能跑与生产可信之间的差距，是本篇的中心问题。选场景时先问"这个查询以后是不是每天都要跑、跑错了有没有人发现"，答不上来就不该直接上 Agent 查数。

### ② 摸现场
- **落实查询前必须先明确五件事**：查哪个对象、看哪个时间、从哪些来源取数、用什么指标、最后要不要把原帖证据一起带回来。任何一件不清楚，系统都无法给出正确结果。这五件事是摸现场的输出物，不是事后补的文档。
- **ES 文档不是一张简单的表**：一篇社媒内容展开后是一份宽文档，含原帖、发帖用户、图片 OCR、视频 ASR、品牌与产品、评论关系、互动快照、模型标签，随着业务需要字段可达数百个。更难的是很多字段看起来相似、实际业务含义不同，AI 选错位置，查询照样跑得出数字，但答案已经不再回答原来的问题。

### ③ 定方案
- **已签字的 POC 边界与验收标准**：来源未披露。文末方法建议是：先选真实高频问题、用难例测试、把高频需求做成 Tool、结果附带证据复核。这是方法建议，不是本项目已签字的验收事实，引用时不能偷换。
- **方案的第一步是"把问题问清楚"**：FDE 的工作排序是先澄清业务问题（报告给谁看、为哪个决策服务、负面是指整帖还是针对某个产品的具体体验、多产品同帖怎么算、要不要附原帖复核），再把这些变成 AI 能理解的条件。业务定义决定结果能不能用，MCP 只是连接器。

### ④ 数据与集成
- **按数据形态与用法选库**：内容多、来源多、查询方式多变的搜索统计用 ES；结构稳定、关系明确的业务数据（如项目、用户、权限、订单）用 PostgreSQL；图片、音频、视频原始文件单独保存。选库的判据是"数据长什么样、别人会怎么用"，不是"哪个库更新"。
- **数据底座就是 FDE-010 清洗后的数据库**：本篇不重复讲清洗，清洗链路见 FDE-010。两篇合读才是"清洗 → 取数"的完整链条，单读本篇会以为取数问题只出在查询层。
- **ES 查询有两棵树**：查询树（哪些数据进来）与聚合树（数据怎么算）。查询能跑通、不报错，不等于算对了。这是本篇对"查询层"最关键的一句提醒。

### ⑤ 开发交付
- **第一次踩坑：AI 直接写 ES 查询**：简单查询可行，但"某款精华的负面评价"会算错人——一篇帖子同时提到两款产品，一款保湿好、一款太黏，AI 只看到"出现该精华 + 帖子有负面"，就把负面算到该精华头上，这类错配非常常见。更多条件还可能漏平台、选错时间、把原帖与评论混在一起。更隐蔽的是聚合方式错：先过滤提到该精华的帖子再数整帖情感，与数针对该精华的具体观点，负面比例会差很多。结论：适合快速验证，太冒险，不适合日报。
- **第二次踩坑：固定查询模板**：产品、平台、时间做成固定选项，AI 只填选择，查询格式变稳、测试可重复。但模板只固定了动作，没固定业务含义："声量"可以是数原帖、数原帖加评论，也可以是数人数，三种算法都讲得通、结果各不相同；模板默认数原帖，就会稳定地给出一个与客户需要不符的数字。结论：稳住了格式，没稳住业务词的意思。
- **第三次踩坑：AI 像分析师一样操作页面（Computer Use）**：复用现有分析系统、无需改后端，演示或偶尔查询没问题。问题在步骤太多：上一轮查品牌 B 的筛选没清干净，下一轮查精华 A 就会混进上一轮的条件；页面还没加载完 AI 就读结果，数字看起来正常、实际是上一轮的旧数或残留条件；按钮位置变化、加载变慢、中途失败都会抬高恢复成本。第一轮通常很顺，第二、第三轮才开始出问题。结论：演示直观，连续任务越来越不可靠。
- **第四次踩坑：直接调原有业务 API**：速度快、跳过界面，但接口是为前端设计的：页面本身知道用户是哪个项目、数据源是什么、每个按钮是什么意思，AI 只拿到一句"查精华 A 的负面口碑"，缺了这些上下文。作者打的比方是饭店收银系统：店员按"招牌套餐"系统就知道是哪些菜，把内部结构直接交给只看到内部编码的外人，对方只能猜。实测结果是速度没问题、数据也返回了，但模型要猜项目、数据源、字段与组合规则，少一个条件可能返回空，条件错了可能返回看起来正常、实际无用的数据。
- **最终解法：Tool 预先定义，MCP 负责发现与调用**：一个 Tool 就是一个具体动作，如查产品口碑、比竞品趋势、找负面增长最快的话题，每个 Tool 预先定义输入与返回格式。以查产品口碑为例，AI 只需要确认产品、平台、时间范围、数帖子还是评论还是人数、要不要带回原帖证据这几项有限条件；内部名称、查询执行、空结果诊断都留在 Tool 内。MCP 是 AI 发现并调用这些工具的标准方式，像一份工具菜单：有哪些工具、每个是干什么的、要填什么。AI 选工具、填几个条件，更像做选择题，而不是现场写一段无界程序。
- **作者的警告必须原样带走**：接入 MCP 本身不会自动保证准确，业务规则仍需人工定义。现有 API 继续负责执行，前面加一层 AI 能理解、业务能检查的工具层。把 MCP 当成准确性保证，是本篇明确反对的误读。

### ⑥ 上线采用
- **已发生的上线与采用情况**：来源未披露。作者给出的采用侧要求是：结果必须附带原帖、评论等证据，以便分析师抽查，报告才敢继续用。这是采用的前提条件，不是采用事实。
- **可执行清单（作者给出的方法，可直接抄）**：从一个真实每天被问的问题出发，不做"通用数据查询 Agent"；按数据与用法选库；把没说出口的条件写清（查谁、查什么、怎么算、给谁用）；用真实难例测试（一帖多产品、一产品多名、原帖加评论）；把高频需求做成 Tool（一 Tool 一动作、输入最少、计算规则固定、失败原因清楚）；通过 MCP 交给 AI；结果必须可验证（附带原帖、评论或其他证据）。

## 对入行者的启示

- **面试答"Agent 查数不准怎么办"，四次踩坑就是失败史**：不要只讲最终方案，先讲四种"看起来能跑、实际不可靠"的解法各错在哪——情感算错人、业务词意思没定、上一轮筛选残留、缺了前端才知道的上下文。讲得出失败史，比只讲成功方案可信得多。
- **数据类交付的验收标准只有一句话**：结果必须附带原帖证据。没有证据的数字，不管跑得多快，都不能直接进报告。
- **FDE 的核心工作排序是"先问清楚，再交给工具"**：报告给谁看、为哪个决策服务、负面是指整帖还是具体体验、多产品同帖怎么算、要不要附原帖复核——这些问题问清之前，写查询、做模板、接 MCP 都是在错误的方向上加速。
- **与 FDE-010 合读，讲"清洗 → 取数"完整链条**：010 解决的是数据怎么洗干净，012 解决的是洗干净之后怎么取数才可信。讲自己的数据项目时，两篇合起来讲，比单讲一篇完整得多。

## verdict

**学，方法极硬的取数专项文。** 四次失败原因都具体，且恰好对应现场最常见的四种"看起来能跑、实际不可靠"的解法；最终解法也没有神化 MCP，反而明确说业务规则仍需人工定义。短板也很明确：这是一篇方法文，不是项目复盘——客户名、周期、成本、准确率、上线与采用事实一概未披露，A 级给的是方法密度与可迁移性，不是完整度。读的时候按"四次踩坑 + 七条清单"用，别按战绩引用。
